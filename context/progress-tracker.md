- **Needed by Step 3 — risk budget vs. single-trade cap interaction.** Worked example (BTC $76,851, balanced appetite, 3% stop): the risk-budget-implied notional is $3,333 (33% of NAV), but the 20%-of-NAV single-trade cap clamps it to $2,000, dropping actual risk-at-stop to 0.6% of NAV rather than the nominal 1%. The crossover is a 5% stop — tighter and the budget governs, wider (i.e. most real crypto stops) and the cap governs. Not wrong, but worth deciding deliberately: raise the cap, lower the budget, or accept it as-is.

Do not resolve these by silently inventing behavior. Resolve them when the relevant implementation unit requires them and record the decision here.

## Architecture Decisions

- The Chrome extension is a UI/control surface, not the autonomous engine.
- The autonomous loop runs in Supabase Edge Functions.
- Supabase Cron/pg_cron triggers the loop every 3 hours.
- V0 uses one LLM call per cycle covering BTC and ETH.
- Technical indicators are deterministic code.
- Risk enforcement is deterministic code.
- Paper execution is deterministic code.
- ~~V0 is long-or-flat and paper-only.~~ **Superseded 2026-09-18** — position model is now FLAT/LONG/SHORT (`context/specs/trading-domain-contract.md`); still strictly paper-only and unleveraged, that part didn't change.
- All decisions, including HOLDs and skipped cycles, are persisted.
- Exact model input payloads are persisted for later replay/evaluation.
- News is treated as untrusted input.
- The decision interval is configuration, even though V0 starts at 3 hours.
- Event-driven triggers are deferred to V1.
- Gemini access for V0 uses 3 rotating free-tier API keys behind the `callModel(payload)` seam: try key 1, fall through to key 2 then key 3 on quota/failure, skip-and-log the cycle if all three fail. Launch moves to a single paid-tier key — a config change behind the same seam, not a code change. **Not yet reflected in `CLAUDE.md` / `architecture.md` / `code-standards.md`** (all three currently describe `callModel` as a single-key abstraction) — update those files when Step 6 (Gemini decision seam, position-model plan numbering — was "Next Up #2" under the pre-pivot sequence) implements this, per `code-standards.md` § Keeping Docs in Sync.
- **Gemini model: `gemini-2.5-flash`** (user, 2026-09-18) — resolves the former "exact model identifier" open question. Treated as a code-level constant in the Gemini seam implementation, not an env var or an `agent_settings` column — consistent with the existing decision (below) that prompt/model versions are execution-time facts recorded on `agent_runs`/`agent_decisions`, not user-tunable configuration.
- **Secrets mechanism for the 3 Gemini keys**, set up ahead of the Gemini seam unit so there's a correct place for them the moment they exist: one gitignored root `.env` (template committed as `.env.example`), read two ways by design — locally via Deno's native `--env-file` flag for smoke-test scripts (same pattern as `coingecko.live-check.ts`/`rss-news.live-check.ts`), and pushed to the deployed Edge Function's actual secret store via `supabase secrets set --env-file=.env` (confirmed live via `--help`, not assumed) — never a plain checked-in file the function ships with. Variable names: `GEMINI_API_KEY_1/2/3`. Explicitly never `VITE_`-prefixed anywhere — Vite inlines any `VITE_*` var straight into the client bundle, which would ship a Gemini key inside the publicly-readable Chrome extension (invariant 2).
- **`context/specs/gemini-decision-agent.md` is superseded, not deleted.** It's the pre-pivot decision-agent spec (long-only BUY/SELL/HOLD, raw-percentage sizing, no stops) — kept in the repo history and on disk as a record of the earlier design, but `context/specs/trading-domain-contract.md` is the live reference from 2026-09-18 forward. Step 6 (Gemini seam) rewrites the superseded doc's output-schema and prompt sections rather than working from them as-is.
- **Position/action/short model (2026-09-18, user-directed pivot).** Long+short, one net position per asset (FLAT/LONG/SHORT), explicit actions `OPEN_LONG`/`OPEN_SHORT`/`HOLD`/`CLOSE` (not `BUY`/`SELL` — ambiguous once both directions exist), mandatory SL/TP on every open, position sizing derived from risk-at-stop rather than a raw NAV percentage, and SL/TP execution on an independent 10-minute monitor cycle rather than gated by the 3-hour decision cycle. Full detail, including every accounting formula, is `context/specs/trading-domain-contract.md` — not restated here to avoid two sources of truth.
- **Shorts are 1x unleveraged synthetic paper only** — collateral-equal-to-notional reservation, no margin, no funding, no exchange liquidation. Collateral exhaustion (loss reaching the reserved collateral, at `2× entry`) is a **deterministic close**, not a P&L clamp on a position left open — this was a specific, load-bearing correction the user required (§0 item 5 of the original request) over an earlier draft that would have clamped P&L while leaving the position running.
- **The stop-out re-entry block is an explicitly-labeled proxy for "avoid re-entering the same failed thesis,"** not real thesis matching (asset + direction + elapsed time only) — stated as such in the contract doc so it's never mistaken for something more semantic than it is. `CLOSE` is never blocked by it or by anything else; only re-entry is throttled.
- **The position monitor polls at 10 minutes but replays the 5-minute price series since its last run**, not a single spot snapshot — verified live (2026-09-18) that CoinGecko's `/market_chart` gives 5-minute points (no high/low) while `/ohlc` gives 30-minute candles (with high/low). Detection is data-limited at 5 minutes, not poll-limited at 10 — but this is explicitly documented as an approximation of a real stop order, not a claim of equivalence: sub-5-minute wicks that breach and recover are invisible to it.
- `extension/` owns only Chrome-specific surface (manifest, MV3 lifecycle, `chrome.*` adapters); `src/components/` and `src/features/` (referenced in `code-standards.md` § File Organization) own the React app `extension/` renders.
