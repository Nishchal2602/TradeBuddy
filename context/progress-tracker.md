This supersedes the "one Gemini decision call" framing throughout this file's earlier entries (Steps 6-7, UI steps) — those entries are left as-written since they accurately describe what was true when built; this note is the pointer forward.
- **`atrPct` is a percentage-as-number (e.g. `1.10` meaning 1.10%), while every `*Pct` field derived from it (`stopLossPct`, `takeProfitPct`, the `effective_*` columns) is a fraction (`0.025` meaning 2.5%).** `strategy/rules.ts`'s `stopLossPctFor` does the one real `/100` conversion; a dedicated test (`'unit conversion'`) guards against ever reintroducing a 100x sizing error here. Worth remembering before touching this file again — `calculateATRPercent` (Unit 5) has used this convention since before V1 existed, V1 is just the first place a percentage and a fraction meet in the same formula.
- **`effective_portfolio_risk_ceiling_pct` is `portfolio_risk_ceiling_multiplier × effectiveRiskBudgetPct`, a fraction of NAV (e.g. `0.01125`) — not a USD figure, and not itself bounded to `≤1` the way `effective_max_total_notional_pct` is** (the multiplier can in principle push it past 1, though no realistic config does). The operational USD figure (`portfolioRiskCeilingUsd = that fraction × current nav`) is recomputed fresh per gate call in `index.ts` and never persisted directly — only the fraction is, so re-tuning `nav` doesn't retroactively change what a historical decision's ceiling "was."
- **`agent_decisions.model_vetoed` is `null` whenever no *completed* model verdict exists for that decision** — not just "no model call was attempted." This covers three distinct cases identically: a non-OPEN_LONG candidate (never reaches the veto step), `news_veto_enabled = false` (veto deliberately off), and a veto call or its dependent news fetch that failed (fails closed to HOLD, but is recorded as no-verdict rather than a fabricated `true`) — see Completed's implementation entry for the reasoning on the third case specifically. Never read an absent/null `model_vetoed` as "not vetoed" — check `strategy_version`/`action`/`reasons` for why no verdict exists before drawing any conclusion from its absence.
- **`cron.job_run_details.status = 'succeeded'` does NOT mean the target Edge Function ever ran, or authorized the request — it only means the SQL body executed without a database-level error.** Both this project's scheduled jobs call `net.http_post` (`pg_net`), which is fire-and-forget: the cron job "succeeds" the instant the HTTP request is *queued*, regardless of what status code the target eventually returns. Found the hard way (2026-09-22, market-quotes plan): `position-monitor-10min` showed clean successes for hours while its actual requests were all being rejected 401 by a broken Vault secret (see Current Phase's CRITICAL entry). **To actually verify a cron-triggered Edge Function ran, check its own effects** — a fresh row in whatever table it writes (`agent_runs` for position-monitor, `market_quotes.fetched_at` for market-refresh) — never `cron.job_run_details` alone. `net._http_response` (also queried async, by the request's own `id`) carries the real status code and body if a direct check is needed.
- **Independent market-quote refresh (2026-09-22, implemented — see Completed): a third, deliberately trade-incapable Edge Function.** `market-refresh` imports only the CoinGecko provider and row mappers — never the strategy, risk gate, broker, or either atomic RPC — and touches only `market_quotes`, a new 2-row table separate from `market_snapshots` (the strategy's own immutable per-decision audit trail, unchanged). Runs on its own 5-minute `pg_cron` schedule (`market-refresh-5min`), independent of `agent-cycle`'s manual-only decision cadence and `position-monitor`'s 10-minute exit cadence; `agent-cycle` additionally upserts the same table on every manual run at zero extra CoinGecko cost. No `agent_runs` row and no idempotency key for this function — unlike a decision or a monitor tick, a duplicate refresh is harmless (invariant 10 protects against duplicate *trades*, and there is nothing here to duplicate).
- **The public anon key is a legitimate way to test-invoke any Edge Function directly over HTTPS** (`curl` with `Authorization: Bearer <anon key>`) — Supabase's gateway accepts any valid JWT, privileged or not, to authorize *invoking* a function; what that function's own internal code can then read/write is a completely separate question governed by RLS and whatever `SUPABASE_SERVICE_ROLE_KEY` it holds internally. Used this (2026-09-22) to verify `market-refresh` end-to-end while the shared `service_role_key` Vault secret was broken, without ever needing to fix that secret first or handle its value.
- **`agent_runs.idempotency_key` and concurrency exclusion are two different concerns, not one (2026-09-22, "manual idempotency" plan — see Completed).** A key's *uniqueness* only ever proves "this exact tick/click doesn't already have a row" — it does NOT prove "no other cycle is running right now" unless every possible concurrent invocation is guaranteed to compute the identical key, which a wall-clock-floored bucket only does for invocations landing in the same bucket. Real mutual exclusion for decision cycles comes from `agent_runs_one_running_decision_idx`, a partial unique index on `(kind) where status='running' and kind='decision'` — deliberately scoped to `decision` only, never `monitor` (a wedged monitor row would silently block all SL/TP monitoring, matching the `service_role_key` incident's own lesson about invisible safety failures). `position-monitor` needs no equivalent: `close_position_atomic` is already fully race-safe via its own `won_race` conditional-update return. Any future third kind of decision-cycle-adjacent mutation should ask the same two questions separately — "how do I dedupe a retried tick?" and "how do I stop two of these running at once?" — rather than assuming one key answers both.
- **A `'running'` row that never transitions out is a real, structural risk whenever a mutex depends on `status`** — an Edge Function can crash or hit its wall-clock limit between acquiring the mutex (the `agent_runs` insert) and its own `catch` block running. `agent-cycle` now reaps any `kind='decision', status='running'` row older than 10 minutes immediately before every insert attempt (`cycle/idempotency.ts`'s `staleRunCutoffIso`) — cheap, idempotent under a race, and the only thing standing between a single bad deploy/timeout and every future manual click being permanently blocked.
- **Gemini → TypeSafe Jev (2026-09-22, implemented — see Completed): the model provider changed, the model boundary did not.** Jev occupies exactly the same narrow veto-only slot Gemini did (trading-strategy-v1.md §11-12) — this migration is a provider swap, not a re-litigation of "the LLM proposes vs. vetoes" (that question was already settled by V1). The veto changed shape though: Gemini returned a boolean directly; Jev returns a calibrated probability (`noul`, 0-1) that code thresholds into a boolean via a versioned, explicitly-provisional constant (`JEV_VETO_THRESHOLD` in `model/jev/question.ts`) — see the Completed entry for why the threshold ships unvalidated on purpose and what makes that safe (raw-`noul` persistence, not pre-validation).
- **No provider fallback exists by design, for Jev exactly as it never existed for Gemini** — a total Jev outage means no new entries open that cycle; it does not mean an implicit approval, and it does not mean trying a second model. Exits, SL/TP, `position-monitor`, and every risk control remain entirely independent of any model provider and are unaffected by an outage.
- **CoinGecko has two entirely different free tiers, and this project used the wrong one for its whole lifetime until 2026-09-22.** The fully anonymous public endpoint (no key, what every request used until now) is rate-limited to 5-15 calls/min, shared across ALL of CoinGecko's worldwide anonymous traffic. The free **Demo** API key (register at coingecko.com/en/api/pricing, no card) raises that to a stable 100 calls/min + 10,000/month — the 10,000/month figure CoinGecko's own docs advertise belongs to THIS tier, not the keyless one, a mismatch that looked like an inexplicable rate-limit bug until traced. `providers/coingecko.ts` now sends `Deno.env.get('COINGECKO_API_KEY')` (when set) as the `x-cg-demo-api-key` header on every request, across all three Edge Functions; unset, it degrades gracefully to the old keyless behavior rather than failing. Worth remembering before adding any NEW CoinGecko-calling code: always thread the optional `apiKey` param through, the same way `fetchImpl`/`baseUrl` already are.
- **A blanket "derive direction/branch from the action string right after the early-return guards" pattern is a live trap the moment a new action literal can be added later, not just a style nit (found 2026-09-22/23, Phase 2).** Two independent files had it — `gate.ts` (`proposal.action === 'OPEN_LONG' ? 'long' : 'short'`) and `plan-decision.ts` (the identical shape) — both fixed the same way: an exhaustive per-action `if` chain ending in `const exhaustive: never = proposal; throw ...`, so a future action added without its own branch is a **compile error**, not a silent mis-signing. Apply this shape on sight anywhere a discriminated union is dispatched by a short-circuiting ternary after only 1-2 branches have been peeled off — the bug is invisible until the union actually grows, which is exactly when it's most dangerous.
- **`riskStatus: 'not_applicable'` is reusable vocabulary for "this decision is now a HOLD," not exclusively "the proposal already was HOLD" (Phase 2).** An ADD/REDUCE the gate determines is below the minimum trade notional returns `not_applicable` rather than `rejected` — deliberately, because `not_applicable` already means "nothing to gate," which is exactly the HOLD it's about to become once `index.ts` normalizes `finalProposal` back to the original candidate. This lets one gate call serve both "compute the real numbers" and "signal the normalization," rather than gating twice. Contrast with a genuine `MODIFY_PROTECTION` rejection (e.g. an attempted widen), which stays `rejected` and visibly shows up as a rejected `MODIFY_PROTECTION` in the decision feed — that one is a real denial, not a too-small normalization, and conflating the two would hide real Jev requests that got refused.
- **Confidence is not a uniform safety signal across actions with different risk polarities — a lesson from a rejected draft, not just a design choice (Phase 2).** A single "confidence below X → HOLD" rule looks like a sensible fail-safe until applied to `CLOSE`: normalizing a low-confidence CLOSE to HOLD *keeps risk on*, the opposite of safe. Any future confidence-based gate must be evaluated per-action against what "the safe direction" actually means for that specific action, never applied as one blanket rule — and should be chosen from real observed confidence-vs-outcome data (Phase 2 persists `actionConfidence` and the full probability distribution on every decision specifically so that data can eventually exist), not assumed.
- **An "X may not influence size/price" rule needs to name the actual boundary, or it becomes false the moment the system does something an absolutist reading forbids (Phase 2).** Jev's ADD magnitude genuinely is a sizing input — the accurate invariant, stated in `CLAUDE.md`/`architecture.md`, is "Jev may choose a bounded adjustment magnitude; deterministic code remains the sole authority over final size," not "Jev may not influence size" (which an earlier plan draft said, and which Phase 2 as approved does not honor literally). When a "may not X" rule is about to be written, check it against every code path that's about to exist, not just the ones already built.
